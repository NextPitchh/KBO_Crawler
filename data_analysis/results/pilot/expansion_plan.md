# 전체 확장(7,200경기) 실행 계획서

이 문서는 Stage 0 파일럿(200경기) 검증 + 이닝 완전성 보강(Stage 1) + concurrency
계단식 실측(Stage 2) 결과를 반영한 전체 확장 실행 계획이다.

## 0. Stage 1 — 이닝 완전성 검증/복구 결과 요약

- 파일럿 200경기 재검사: `incomplete_gap`(실제 데이터 손실) 4건, 재수집으로 전부
  복구(투구 수 273→337, 301→323, 240→262, 234→262). 복구 후 재검사 결과
  `incomplete_gap` 0건.
- `short_needs_verification`(최종 이닝 9 미만) 4건은 schedule API `statusInfo`
  ground truth와 대조: 3건은 확정 콜드/서스펜드 게임(정상), 1건
  (`20240724NCHT02024`)은 raw relay를 직접 대조해 "6회초 첫 타자 발표 직후
  투구 데이터 없이 중단"된 진짜 서스펜드로 확인 — 애초에 잃어버린 PA가 없었음.
- 기존 153경기(`data_analysis/results/pbp/`) read-only 재검증: **153/153 전부
  `complete`, gap 0건, short game 0건**. 기존 WPA 계산에 영향 없음 — 안전.
- 파일럿 하위 산출물(PA/WPA/enrichment) 전체 재생성 완료: PA 15,496 → 15,530건
  (+34), WPA 도메인 순서 재검증 PASS(수치 변화는 소수점 셋째 자리 이내로 미미).

## 1. 채택 concurrency와 근거

### Stage 2 계단식 테스트 실측치 (파일럿 200경기와 완전히 분리된 신규 300경기)

| 단계 | concurrency | 대상 | 소요시간 | 경기당 평균 | HTTP 429 | HTTP 5xx | Timeout | 이닝 누락률 | 실패율 |
|---|---|---|---|---|---|---|---|---|---|
| Stage2-1 | 8  | 100경기 | 180.0초 | 1.80초 | 0 | 0 | 0 | 0.0% | 0.0% |
| Stage2-2 | 12 | 100경기 | 124.9초 | 1.25초 | 0 | 0 | 0 | 0.0% | 0.0% |
| Stage2-3 | 16 | 100경기 | 100.2초 | 1.00초 | 0 | 0 | 0 | 0.0% | 0.0% |

3단계(8→12→16) 모두 중단 조건(429 발생/실패율 2% 초과/이닝 누락률 2배 초과) 중
어느 것도 발동하지 않고 전부 통과했다. 계획서상 최고 테스트 단계인 **16을
채택 concurrency로 권장**한다.

### 성능 격차(37배) 원인 규명 — 통제 재측정 (Round 3, Task 1)

Stage 2(16, 3,592경기/시간)와 파일럿(5, 96.9경기/시간)의 격차가 concurrency
비율(3.2배)로 설명되지 않아, **동일 game_id·동일 수집 범위(PBP+preview)·
동일 concurrency=16**으로 통제 재측정을 실시했다.

- 대상: 파일럿에 실제 사용된 200경기 중 시드 고정 샘플 50경기(완전히 동일한
  game_id)
- 캐시 무효화: `data/pbp_pilot/`, `data/preview_pilot/` 기존 파일은 전혀 건드리지
  않고, 새 디렉토리(`data/controlled_retest/`)에 처음부터 재수집 — 동일 효과를
  기존 파일럿 데이터 훼손 위험 없이 달성
- 결과: **PBP 53.4초 + preview 3.2초 = 56.6초, 50경기 → 3,178경기/시간**
  (PBP만 보면 3,370경기/시간) — Stage 2(3,592경기/시간)와 **오차범위 12%
  이내로 일치**, HTTP 상태코드 100% `200`(재시도/실패 0건), 경기당 평균
  요청 수 10.1건(9~10이닝+센티널 요청과 일치, 이상 없음)

**판단(Task 1-3 기준)**: 재측정 결과가 Stage 2 속도에 근접(96.9경기/시간과는
33배 차이, 3,592경기/시간과는 1.13배 차이) → **파일럿이 스로틀링되었다는
결론을 통제 실험으로 확정**한다(요청 수 대조에서도 스코프 차이·재시도
과다·캐시 효과 등 다른 설명은 모두 배제됨 — 원인은 파일럿 실행 중 장시간
무인 대기 구간에서의 세션/컨테이너 유휴 스로틀링으로 추정, 정확한 인프라
레벨 원인까지는 이 환경에서 직접 확인 불가하나 대안 설명이 모두 소거되어
가장 유력). **기존 concurrency=16 채택 계획을 그대로 유지**하며, 아래
"예상 소요 시간"은 이제 추정이 아니라 통제 재측정으로 뒷받침된 수치다.

다만 무인 장시간 실행 자체의 리스크(세션 유휴 등 외부 요인)는 여전히
남아있으므로, 연도 단위 분할 실행 원칙(4절)은 유지한다.

## 2. 연도별 실행 순서 (2025 → 2016 역순)

최신 연도부터 역순으로 실행한다. 근거:
- 최신 연도일수록 스키마가 안정적이고(`wpaByPlate` 등 신규 필드 완비, 2-2 참고)
  모델 학습에 더 관련성 높은 데이터라 먼저 확보해 두면 중간에 중단되어도
  가장 가치 있는 데이터부터 이미 확보된 상태가 된다.
- preview API가 2017-05-30 이전을 아예 제공하지 않으므로, 2016~2017년 상반기는
  bullpen/lineup 정보 없이 PBP만 확보되는 특수 구간이다 — 뒤로 미뤄 마지막에
  처리하면 "완전한 데이터부터 우선 확보"라는 원칙과 일치한다.

실행 순서: 2025 → 2024 → 2023 → 2022 → 2021 → 2020 → 2019 → 2018 → 2017 → 2016

각 연도는 `data/game_ids/all_games_{year}.txt`(이미 game_id_collector.py로
전수 수집됨, `is_regular_season=True`인 game_id만 필터링)를 그대로 입력으로 쓴다.

## 3. 세션당 처리량과 예상 소요 시간

concurrency=16 실측(3,592경기/시간) 기준:

| 항목 | 예상치 |
|---|---|
| PBP 크롤링 전체(7,200경기) | 약 2.0시간(연속 실행, 방해 없을 시) |
| preview 크롤링(2017-05-30 이후 대상 약 6,100경기, 순차 1.0초 간격) | 약 1.9시간 |
| PA집계+WPA+enrichment | 수 분 이내 |
| **합계** | **약 4시간 (낙관적 하한)** |

보수적 계획(세션 유휴 등 외부 요인 대비 여유):
연도별로 나누어 실행 시 720경기/연도 ÷ 3,592경기/시간 ≈ **연도당 12~15분**
(concurrency=16, 연속 실행 조건) — 세션 하나에 2~3개 연도씩 묶어도 1시간
이내로 충분히 끝난다. 통제 재측정으로 처리량 자체는 확정됐지만, 파일럿에서
관측된 "장시간 무인 대기 시 스로틀링" 리스크는 여전히 남아있으므로, 실제
운영 시에는 **연도 단위로 나누어 실행하고 매 연도 종료 시 6절 체크포인트를
거치는 것을 권장**한다(한 번에 7,200경기를 무인으로 돌리지 않음 — 문제
발생 시 조기 발견 가능).

## 4. Resume 지점 관리 방식

- 기존 파이프라인의 CSV 존재 여부 기반 스킵(Resume) 로직을 그대로 재사용한다
  (`run_hsk.py`/`run_pilot.py`와 동일 패턴: 파일 존재 = 이미 수집됨 → 스킵).
- 출력 디렉토리를 연도별로 분리한다: `data/pbp_full/{year}/{game_id}.csv`,
  `data/preview_full/{year}/{game_id}.json`. 연도 단위 디렉토리 분리로
  "어느 연도까지 끝났는지"가 파일시스템 상태만으로 명확해진다(별도 상태 파일
  없이도 `ls data/pbp_full/` 로 진행 상황 파악 가능).
- 연도 하나를 시작하기 전, 그 연도의 `all_games_{year}.txt` 대비 이미 존재하는
  CSV 개수를 세어 "N/720 완료"를 출력하고 시작한다(진행 로그).
- 세션이 중단되면(타임아웃, 수동 중단, 장애) 그냥 같은 명령을 재실행하면 된다 —
  Resume 로직이 자동으로 완료분을 스킵하므로 별도 체크포인트 파일 관리가
  불필요하다.

## 5. 실패 경기 처리 정책

- **이닝 단위 부분 실패**: `kbo_crawler/inning_retry.py`의
  `recover_games_in_dir()`를 크롤링 루프에 통합 — 매 경기 크롤링 직후
  `inning_completeness.check_game_completeness()`로 즉시 검사하고,
  `incomplete_gap`이면 그 자리에서 누락 이닝만 최대 3회 지수 백오프 재시도.
  재시도 후에도 실패하면 **그 경기의 CSV를 저장하지 않는다**(부분 데이터
  절대 사용 금지 — Stage 0/1에서 확립된 원칙 유지).
- **short_needs_verification(최종 이닝 9 미만)**: 즉시 실패 처리하지 않고
  `data/game_ids/`에 이미 확보된 schedule API 접근 경로로 ground truth
  (`statusInfo`/`suspended`/`cancel`)를 대조해 "확정 콜드게임(called)"과
  "크롤링 결함"을 구분한다(Stage 1에서 검증된 방법론 — 실제로 4건 중 3건이
  `suspended=False`·승자 확정된 정상 콜드게임, 1건은 "6회초 첫 타자 발표
  직후" 상태에서 콜드 처리된 것으로 raw relay 직접 대조까지 마쳐 PA 손실
  자체가 없음을 확인. **4건 전부 API 공식 분류상 "suspended"가 아니라
  "called"**임에 유의 — 6절에서 다루는 called 정책이 이 4건 모두에 적용됨).
- **완전 실패 경기**(재시도 3회 후에도 gap 존재): `data/game_ids/failed_games_{year}.txt`
  에 game_id + 실패 사유를 기록하고 다음 연도로 진행한다(전체 파이프라인을
  막지 않음). 연도 완료 후 failed 목록을 모아 별도 세션에서 재시도.
- **HTTP 429 대응**: concurrency_probe.py에서 검증된 대로, 429가 한 건이라도
  감지되면 그 크롤링 세션을 즉시 중단하고 concurrency를 한 단계 낮춰 재시작한다
  (전체 확장 크롤러에도 같은 abort_event 패턴을 이식할 것을 권장).

## 6. 중단 경기(game_status) 처리 정책

### 6-1) 분류 (`kbo_crawler/game_status_scan.py`, 신규)

기존 `game_id_collector.py`(재사용, 수정 없음)의 schedule API 원본에서
`cancel`/`suspended`/`statusInfo` 필드를 그대로 살려 4가지로 분류하고
`game_index.csv`에 `game_status`/`status_info` 컬럼으로 병합했다
(취소 경기 등 원래 `game_index.csv`에서 빠져 있던 상태까지 포함한 전수는
`game_index_all_statuses.csv`에 별도 저장):

- `normal`   : `statusCode=='RESULT'`, 취소·서스펜드 아님, 최종 이닝 ≥ 9
- `called`   : 위와 동일하되 최종 이닝 < 9 (콜드게임, 승자 확정)
- `suspended`: `suspended==True` (재개 예정 — **API 필드 기준으로 2016~2025
  전체에서 실측 0건**. 향후 데이터에 나타날 수 있어 정책은 유지하되, 현재
  이력 데이터에는 해당 사례가 없음이 확인됨)
- `cancelled`: `cancel==True` (경기 자체가 열리지 않음 — statusInfo="경기취소")

### 6-2) 처리 정책 (기본값, `data_analysis/methods/called_game_correction.py` 신규)

- **normal**: 그대로 사용.
- **called**: 정상 사용하되, 그 게임의 **마지막 PA**(경기 전체 기준, 이닝
  마지막 아님)에 대해 `we_after`를 "경기 확정 결과"로 덮어쓴다 — 공격팀이
  승리로 끝났으면 1.0, 패배로 끝났으면 0.0, 그에 맞춰
  `reward_wpa_computed = we_after − we_before`도 재계산한다.
  `state_transition.py`/`inject_wpa.py`는 수정하지 않고, 그 산출물 위에
  적용하는 독립 후처리 단계로 구현(`apply_called_game_correction()`).
- **suspended**: **제외**. 중단 시점의 WE가 최종 결과와 무관하므로 WPA
  계산이 왜곡된다. 제외 시 `data/game_ids/excluded_games.csv`에 사유
  (`suspended_pending_resume`)와 함께 기록.
- **cancelled**: **제외** (경기 자체가 없어 PBP 데이터도 없음 — 크롤링
  대상에서 애초에 제외). 동일하게 `excluded_games.csv`에 사유
  (`cancelled_before_game`)로 기록.

### 6-3) 콜드게임 WPA 보정 검증 (파일럿 4건 실측)

파일럿의 called 4건(`20210901WOSS12021`, `20230404LTSK02023`,
`20240724NCHT02024`, `20250719HHKT02025`) 전체에 보정을 적용해 검증했다:

| game_id | 최종 스코어 | 보정 전 we_after | 보정 후 we_after | reward_wpa_computed 변화 |
|---|---|---|---|---|
| 20210901WOSS12021 | HOME 7:1 승 | 0.974 | **1.000** | −0.015 → +0.011 |
| 20230404LTSK02023 | HOME 3:1 승 | 0.881 | **1.000** | −0.063 → +0.056 |
| 20240724NCHT02024 | HOME 7:0 승 | 0.961 | **1.000** | +0.028 → +0.067 |
| 20250719HHKT02025 | AWAY 6:5 승 | 0.707 | **1.000** | +0.011 → **+0.304** |

보정 전에는 4건 모두 we_after가 1.0에 못 미쳤고, 특히 접전으로 끝난
`20250719HHKT02025`(6:5)는 오차가 0.293에 달했다(state_transition이 "다음
공수 전환"을 가정해 마치 경기가 계속되는 것처럼 확률을 낮게 계산했기 때문).
2건(`WOSS12021`, `LTSK02023`)은 보정 전 `reward_wpa_computed`가 **음수**로
찍혀 있었다 — 즉 "경기를 확정 짓는 결정적 플레이가 승리 확률을 깎아먹었다"는
모순된 신호가 이미 학습 데이터에 들어가 있었던 것. 보정 후 전부 부호가
정상화(양수)되었다. 보정 적용 후 파일럿 WPA 도메인 순서(`HR>3B>2B>1B>BB>
SF>OUT>SO>GDP`)는 그대로 유지됨을 재확인했다(PASS).

### 6-4) 전체 확장 예상 규모

`game_index.csv`(정규시즌 7,197경기) 기준 실측:

| game_status | 건수 | 비중 |
|---|---|---|
| normal | 7,159 | 99.47% |
| called | 38 | 0.53% |
| suspended | 0 | 0% |
| cancelled | (정규시즌 범위 밖 별도 집계, 크롤링 대상 아님) | — |

7,200경기 확장 시 called 게임은 약 38건(±소수) 발생 예상 — 전량 6-2 정책으로
보정 처리하면 되고, suspended는 과거 데이터 기준 발생 이력이 없어 예외 처리
경로만 준비해두면 충분하다. `cancelled`(전체 스캔에서 770건 발견,
전부 `statusCode=='BEFORE'`+"경기취소" — 취소된 경기는 통상 다른 날짜에
더블헤더로 재편성되어 별도 game_id로 정상 존재하므로 실질적 데이터 손실
아님)는 애초에 `game_id_collector.py` 단계에서 걸러지므로 크롤링 파이프라인이
따로 처리할 필요가 없다.

## 7. 중간 검증 체크포인트 (연도별)

각 연도 크롤링 완료 직후, 다음 연도로 넘어가기 전에 반드시 확인:

1. **경기 수**: `all_games_{year}.txt` 대비 성공적으로 저장된 CSV 수
   (실패 목록 제외 시 100% 일치해야 함)
2. **이닝 완전성**: `check_pbp_dir(f"data/pbp_full/{year}")` 실행 →
   `incomplete_gap` 0건 확인 (있으면 그 해 진행을 멈추고 원인 조사)
3. **PA 집계 UNK 비율**: `aggregate_pa()`의 UNK 비율이 5% 초과하면 중단하고
   regex 패턴 보강 필요 여부 확인(연도별 relay_text 표현 변화 가능성)
4. **WPA 도메인 순서**: 그 해 데이터만으로 `HR > 3B > 2B > 1B > BB > SF > 0 >
   OUT > SO > GDP` 순서가 깨지지 않는지 확인 — 깨지면 절대 다음 연도로
   진행하지 않고 즉시 보고(전체 확장 절대 금지 규칙)
5. **팀 커버리지**: 그 해 등장해야 할 팀 코드가 모두 존재하는지
   (`game_index.csv` 기준 기대 팀 목록과 대조)
6. **preview 커버리지**: 2017-05-30 이후 연도는 preview 실패율이 파일럿
   실측치(0%)에서 크게 벗어나지 않는지 확인
7. **game_status 검증**: 그 해 `called` 게임 전부에 6-2 보정이 적용됐는지,
   `suspended`/`cancelled`로 분류된 게임이 정말 `excluded_games.csv`에
   기록되고 PA 데이터셋에서 빠졌는지 확인
